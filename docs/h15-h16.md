# Validation and recovery notes

## Pinned behavior

- Mainnet H15: DAA 140,115,000; H16: DAA 147,000,000.
- Testnet H15: DAA 3,500; H16: DAA 180,000.
- H15 PoM v5 verification and H16 pad sizing come from the pinned official Rust implementation, not from miner-reported prefix values.
- Service strikes come from `GetServiceStrikes` (wire fields 1120/1121). Current requests and audit draws come from `GetAwaitedOpenings` (1126/1127).
- A request uses its computed transaction ID, not a prefix of its payload. Ownership, model, token commitment, signed response, audit draw/seed, path, parent-phase root and deadline are checked before publication.
- `verifier/src/audit.rs` adapts the private opening-check functions from the pinned node's `consensus/core/src/collateral.rs`. Public cryptographic verification still uses that pinned node's verifiable-inference crate. Review this adapter when changing the pin.

## Observed validation boundary

Validated on 2026-11-11. The initial contribution was static-only. After explicit authorization, automated tests and an isolated real Windows/RTX 5080 mining trial were executed on `keryx-testnet-10`, with fresh test-only keys and the official miner/node release assets.

Observed results: Windows Go build PASS; Go vet PASS; govulncheck v1.9.0 PASS (no known vulnerable symbols, imported packages or required modules with the selected versions); locked Cargo check, Clippy with warnings denied, and release build PASS. All 35 Go test functions passed with race detection, as did eight Rust tests, five native verifier protocol checks and 160 loopback network/status checks (eight distinct checks repeated 20 times). The inherited third-party-pool snooper is explicitly skipped by automated tests. Docker and Linux builds were not run.

The final real H16 trial independently re-read and hash-checked 396 distinct node-accepted blocks at DAA 545,178–545,557, using Gemma-4-12B on the official miner v0.6.1 and node v1.6.7. The bridge was race-instrumented and built from clean commit `c2fbcf3878bdb2caaedbe1aaf4fb137b7406c2c3`. Complete logs were checked after disconnect and process cleanup. This is node block acceptance on testnet, not mainnet reward qualification or proof of a complete inference/audit cycle. See [the test record](validation/h16-testnet-20261111.md), including the earlier 222-block run and the intermediate disconnect regression.

The runtime checks exposed and fixed an ignored legacy challenge that prevented job admission, rejection of network-valid blocks above a harder pool share target, a nil legacy escrow-store call, unsynced zero-strike reporting, and listener/test-socket shutdown races. Repeated identical model declarations are acknowledged; changing the declared model set remains forbidden within a session.

Build and automated checks to reproduce:

```sh
go build -mod=readonly -trimpath -o bin/keryxbridge ./cmd/keryxbridge
go vet ./...
go test -race -count=1 -timeout=60s ./...
go run golang.org/x/vuln/cmd/govulncheck@v1.9.0 ./...
cargo check --locked --all-targets --manifest-path verifier/Cargo.toml
cargo test --locked --manifest-path verifier/Cargo.toml
cargo clippy --locked --all-targets --manifest-path verifier/Cargo.toml -- -D warnings
cargo build --release --locked --manifest-path verifier/Cargo.toml
```

The scan is limited to known Go vulnerability records and reachable Go calls. It does not audit the Rust dependency graph, inherited C code, operating system or deployment. It is not a security certification.

Runtime qualification remains NOT_RUN for the historical H15-only interval, other models, a full on-chain private inference/audit cycle, mining/inference transitions, node outages, reconnect/restart with retained traces, every attention phase, reorg recovery, queue pressure, pool-scale performance, remote TLS/tunnel interoperability, mainnet operation and escrow recovery. These limits accompany the H15/H16 compatibility and escrow-strike contribution for code review; the bounded testnet mining pass is not complete deployment qualification.

## Failure and recovery

The state file contains encrypted request payloads and signed publications, not decrypted prompts or worker tokens. Protect it because it binds a response to the worker retaining its trace. A helper timeout or broken pipe closes verification; an operator restart is required. The bridge never switches to prefix-only proof acceptance.

RPCs have request deadlines, and signed publication retries reuse exactly the persisted envelope. Mempool admission is not chain acceptance. Node obligations decide which requests may be served and which opening pieces remain owed. An absent, failed or stale node observation is never replaced by a zero-strike claim.

The chain scan retains up to 8,192 selected-chain draw candidates and walks at most 2,048 blocks to reconcile a checkpoint. Initial startup samples 128 selected-chain blocks and their blue merge blocks. This initial bounded backfill is not a general recovery of historical service obligations. Use a fresh dedicated key, or reconcile existing obligations and retain the previous state/worker traces before migration. An unknown owed opening or a checkpoint outside the scan limit blocks new mining work instead of manufacturing a worker or seed.

There are at most 1,024 retained tasks and 128 configured worker identities. File/line, proof, helper reply and audit bundle sizes are bounded. Capacity exhaustion requires reconciliation; it does not discard an owed audit. Worker assignment before a prepared response may be retried or reassigned; after preparation it stays with the authenticated worker identity retaining that response's trace. Tokens and worker identities must not be shared between independent machines.

Configuration is for one payout identity. A public multi-account pool needs separately designed ownership, accounting, isolated signing, admission, privacy, payments and monitoring policies. Third-party pool policies and payments are outside this update.
